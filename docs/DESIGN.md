# 設計の考え方：Opus（Claude Code）だから進んだのか、固定フローにできるのか

> novel_studio v1.0 の設計の元になった考察です。材料は、元のリポジトリ [novel-tools](https://github.com/InfraOjisan/novel-tools)（テスト小説と実験の記録）です。

- 日付：2026-10-12
- 材料：novel-tools の検証記録・アイデアの種・グラウヴァル第6回の制作メモ・公開エンジニアリングのまとめ、70コミット（`Novel_1`〜`Series_Grauwall/Grauwall_06`）
- 結論を先に：**①と②のどちらか、ではなく、仕事の層で分かれる。** 作品づくりの流れは②（固定フロー）にでき、v1.0 でアプリにした。固定できない残り（道具の改修と、BRIEF を書く創作力）が、①（他のハーネス × モデル）で本当に試すべきところで、そのための試験を作った。

---

## 1. 問いの立て直し

「Claude Code の Opus 5.5 だからスムーズに進んだ」は正しい。ただし、Opus が何をしていたかを分けると、ハーネスの力とモデルの力が混ざっている。

第6回『白塔の使者』の実績（制作メモ 2-1）：上位モデル（Claude）が入ったのは**設計の修正2回・章の手直し5回・校正1回**。残りの約90回の呼び出しは安いモデル（haiku-5.5 と luna-pro）。費用はドル単位に届かない。

一方で、記録に残っていない Opus の仕事がある。

| Opus がやっていたこと | 記録での見え方 | 種類 |
|---|---|---|
| BRIEF（第6回は 53,493 字）を書く | 「Claude が BRIEF を作成」 | **モデルの創作力** |
| 作品ごとに CANON テンプレート・LEDGER の欄・プロンプトを手で合わせる | `templates/` と `prompts/` が作品ごとに違う（第6回は「エルノ」「白塔」入り） | **手合わせ**（機械化できる） |
| `config.json` の `slot_plan` を BRIEF の配置表と手で合わせる | `_comment_series`：「slot_plan は BRIEF.md 第4-2節と必ず同時に変更する」 | **手合わせ**（機械化できる） |
| CANON の審査が収束しないとき、全体を通して直す | 「haiku と luna の往復が収束しなかったので、Claude が2回、全体を通して直した」 | **モデルの力**（一回の API 呼び出しにできる） |
| 通らない章を、指摘箇所だけ直す | 第4・6・14・16・20章 | 同上 |
| 全文の校正（22件）を `proofread_apply.py` の Python のリストに書く | `EDITS = [...]` がコードの中にある | 同上（JSON にすれば機械化できる） |
| 推論の暴走・締め切り・パケットの食い違いを、ログから診断してコードを直す | 第6回だけで novelctl の改修 10 件 | **ハーネス × モデルの力**（固定できない） |
| 実験の設計と分析（evolve・mask・compe） | Novel_4 | 同上 |

つまり、Opus への依存は4種類に分かれる。

## 2. 層ごとの判断

| 層 | 中身 | 固定フロー化（②） | 他ハーネス（①） | v1.0 での扱い |
|---|---|---|---|---|
| A. 上流の創作 | テーマ → 企画 → 分類 → BRIEF | **できる**。BRIEF を JSON で出させ、BRIEF.md・config・CANON テンプレートを機械で描き出せば手合わせが消える | 道具を順に動かすのは易しい。BRIEF を自分で書くのはモデル次第 | `studio/`（アプリ）と `engine/tools/scaffold.py` |
| B. 進行 | CANON → 章 → 台帳 → 最終審査 | **既にできていた**（novelctl） | 弱いハーネスでも可（止まるべきところで止まれれば） | `engine/`（Grauwall_06 の最新版を汎用化） |
| C. 例外処理 | CANON の全体修正・章の手直し・校正 | **できる**。ハーネスではなく上位モデルを API で一回呼ぶ工程にする | 「呼ぶかどうか」の判断だけが残る（人の許可） | `novelctl rescue canon` / `rescue chapter N` / `proofread`（役 `premium`） |
| D. 道具の改修 | ログからの診断とコードの修正 | **できない**（毎回違う） | **ここが本当の検証対象** | `harness/exams/` の L4 |

②にできた理由は、Novel_4 以降に積んだ知見が、そのまま設計の規則になっていたから。

- 合議は外れ値を生まない → 分類は良し悪しではなく「型への寄り方」を見せ、外れ値を拾うのは人。外れ値を増やすのは「収束した骨格を避けて」の再提出（ローリング）。
- 重複の判定は LLM に任せない（審判の自己一致 ARI 0.115〜1.0） → 骨格の抽出だけをモデルに頼み、近さは道具が数える。
- 品質の天井は書き手が決める／安いモデルは全体の整合を取りながら直すのが苦手 → 書く・照合は安いモデルで何度でも、全体の整合は上位モデルで一回だけ。
- AI の報告は鵜呑みにできない（dsp・lc：78%） → 校正案は「原文が原稿に一か所だけある」ものしか通さない。ハーネスの試験は報告ではなくディスク上の状態で採点する。
- 同じ事実が二か所に書かれていると必ず食い違う／書いていない世界の前提は安いモデルが現代の常識で埋める → CANON テンプレートに「世界の前提（効く範囲つき）」の節を必須にした。

## 4. まだ分かっていないこと（正直に）

- **本物のモデルでは一度も回していない。** すべて偽モデルでの確認。最初の本番では、提案・骨格・BRIEF の JSON を各モデルが書式どおりに返すか、BRIEF の質が手書きの5万字にどこまで迫るかを見る必要がある。
- **上位モデルの OpenRouter での名前**を `anthropic/claude-opus-5.5` と仮に置いた。違えば `config.default.json` と studio の設定で直す。Novel_5 では「Opus は OpenRouter 経由だと高いので agy で」という判断があった。studio の上位モデルの役を agy につなぐ接続部は v1.0 に入っていない（issue にした）。
- **BRIEF の JSON は手書きの BRIEF より薄い。** 第6回の BRIEF にあった「プロデューサー確認事項」「長い糸の置き方」「シリーズの規律」は、汎用の欄では表せない。シリーズものは当面、手書きの BRIEF＋今の Grauwall の流れのほうがよい。
- **分類のしきい値（0.5）は偽モデルでしか合わせていない。** 本物の案で、人の「似ている」と道具の「似ている」が合うかを確かめる。
- 作品フォルダに道具を複製する方式は変えていない（保護ファイルの指紋の仕組みを壊さないため）。パッケージ化は issue にした。

## 6. 新しい発想の種（この整理から出たもの）

1. **「上位モデル依存度」の診断。** 業務の流れを、安いモデルで回したときに「どこで止まり、上位モデルの一回で通るか」を数えると、その業務の上位モデル依存度が出る。第6回は 8/98。AIOps の運用設計で「どの工程に高いモデルの予算を置くか」を決める根拠になる。`rescues` の数がそのまま KPI。
2. **ハーネスの誠実性ベンチ。** L1・L2 は賢さではなく、止まる・許可を守る・確かめたことだけを報告する、を測る。報告ではなくディスクの状態で採点する方式は、業務エージェントの採用試験として小説の外でも使える（チケット対応、変更管理、障害一次対応に置き換えるだけ）。「業務 AI に要るのは誠実さ」を数字にする道具。
3. **仕様書の lint。** BRIEF を JSON にして機械検査したら、「回収が設置より前」「章数の不一致」のような構造の誤りが書く前に消えた。企画書・要件定義・変更申請も、同じように「構造だけは機械が確かめ、中身は人とモデルが書く」形にできる。台帳（作成 → 変更は承認つき → 反映 → 棚卸し）の考え方とそのまま重なる。
4. **企画の分類を社内の未来計画に。** studio の「提案 → 骨格の抽出 → ルールで分類 → 収束を避けて再提出」は、小説に固有の部分が prompts/ と similarity.py の欄だけ。base_url は OpenAI 互換なら差し替えられるので、社内の model router（匿名化つき）に向ければ、半年より先の計画づくりにそのまま使える。骨格の欄を「誰が困っているか・何が変わるか・何が前提か・何がひっくり返るか」に替えれば、事業案の型への収束が見える。
5. **外れ値の予言台帳。** 分類で「外れ値」になった案を日付つきで台帳に残し、半年〜1年後に「当たったか」を照合する。仮説を立て、時間が経ってから確かめる道具。外れ値は合議では生まれず、人が拾うしかない──だからこそ、拾った外れ値の当たり外れの記録は、その人の目利きの記録になる。
6. **「固定できない層」を売り物にしない設計。** 道具の改修（D 層）だけは毎回違う。ここを人＋最上位モデルの仕事として明示し、それ以外を固定フローに落とすと、運用の費用が「固定部分×回数＋例外×単価」で見積もれる。受託の見積もりやサブスクの価格設計の型になる。
